# v0.1 — Agent Kernel Prototype

## 1. 背景

当前项目还没有可运行的 Agent runtime。用户的最终目标是纯前端、无后端、浏览器扩展内运行的浏览器 Agent，但在做页面工具和 UI 前，必须先证明最小 loop 能稳定运行。

当前用户遇到的问题：没有统一的 AgentDecision、ToolSpec、ToolResult、TraceEvent，也没有模型调用抽象、tool registry、结构化输出解析和错误处理。

现有系统限制：无法判断模型输出是否合法，无法统一执行工具，也无法复盘一次 agent run。

为什么现在要做：v0.1 是后续 a11y tools、cockpit UI、form/debug、memory 和 workflow replay 的地基。

## 2. 用户故事

US1. 作为产品开发者，我希望在没有后端的情况下运行一个最小 agent loop，以便验证 BrowserHelm 的核心方向可行。

US2. 作为开发者，我希望模型输出必须通过 schema 校验，以便避免自然语言或坏 JSON 直接驱动工具。

US3. 当模型输出不合法时，作为开发者，我希望系统产生可诊断错误和 trace，以便定位是 prompt、parser、schema 还是模型问题。

US4. 作为后续工具开发者，我希望有统一 ToolRegistry 和 ToolResult，以便新工具可以按统一协议接入。

US5. 作为 runtime 开发者，我希望 v0.1 就有 loop turn、loop session 和 loop control 的最小概念，以便后续 pause/resume、approval、trace 和 UI 都有统一基础。

US6. 作为安全设计者，我希望 tool risk 和 approval_required 能进入协议层，以便高风险动作从第一天就不能绕过 trace 和 policy。

US7. 作为调试者，我希望模型输出解析失败时能在 trace 里看到 raw output、parse error 和使用的 prompt/schema/context policy 版本。

US8. 作为后续评测开发者，我希望每个 step 有时间戳和耗时，以便未来统计 latency、maxSteps 和失败率。

US9. 作为 agent runtime，我希望 v0.1 能记录目标和当前 step 意图，但不要求提前生成完整计划。

## 5. 产品方案

### 功能入口

开发者通过 dev script 或测试入口启动一次测试 run。v0.1 不实现 React DevRunner，也不引入正式 Cockpit UI。

dev script 默认使用 mock model，开发模式下允许读取项目 `.env` 作为 OpenAI-compatible client 的 fallback 配置：

- `OPENAI_BASE_URL`
- `OPENAI_API_KEY`
- `OPENAI_MODEL`

真实模型调用只作为本地手动验证，不作为默认单测或 CI 的依赖。

### 用户路径

输入任务 -> AgentLoop 创建 loop session -> 执行 loop turn -> 构建 compact context -> ModelClient 返回 decision -> DecisionParser 校验 -> ToolRouter 执行 mock tool -> TraceRecorder 写入完整结果 -> ContextCompactor 生成下一轮摘要 -> finish/fail/ask_user。

v0.1 只做 Goal + Turn：Agent 知道任务目标和当前 turn 的 intent，但不生成完整 plan。

dev script 最小能力：

- 输入测试任务。
- 运行一次 mock 或真实 provider-backed run。
- 在终端输出当前状态、最终输出和 trace JSON。

### 正常状态

一次 run 至少包含 `run_started`、`turn_started`、`model_output_received`、`model_decision`、`tool_result`、`context_summary`、`run_finished` trace。

### 空状态

没有可用模型配置时返回 `PROVIDER_NOT_CONFIGURED`。

### 错误状态

模型输出非法、tool 不存在、tool args 不合法、模型请求失败都必须进入 fail state。

### HITL 协议状态

v0.1 不显示审批 UI，但必须能表达：

- tool 声明 `risk`。
- ToolResult 可以返回 `requiresApproval` 和 approval preview。
- AgentLoop 可以进入 `waiting_for_approval` / `paused` 状态。
- trace 可以记录 `approval_required`。

### 权限 / 可见性

不涉及页面权限。API key 配置只保留接口骨架，不要求 UI。

## 7. 技术方案

### 现状

无 agent runtime。

### 目标设计

建立独立 agent kernel。Agent kernel 不直接触碰 DOM，不依赖 UI，不依赖后端，也不依赖 chrome extension runtime。v0.1 可以用 dev script 或测试入口启动，但 agent 层本身必须能在 Node/Vitest 环境单独测试。

### 数据流 / 调用链

输入 -> LoopSession -> LoopTurn -> ContextBuilder -> ContextCompactor -> PromptBuilder -> ModelClient -> DecisionParser -> ToolRouter -> TraceRecorder interface -> context summary -> 输出。

### 关键类型 / API

```ts
type AgentDecision =
  | {
      type: 'tool_call';
      tool: string;
      args: Record<string, unknown>;
      reason?: string;
    }
  | { type: 'ask_user'; question: string }
  | { type: 'finish'; message: string }
  | { type: 'fail'; message: string; code?: string };

type ToolRisk = 'safe' | 'low' | 'medium' | 'high';

type ToolMode =
  | 'ask'
  | 'debug'
  | 'form'
  | 'act'
  | 'vision'
  | 'advanced'
  | 'memory'
  | 'internal';

type ContextPolicy = {
  maxRecentSteps: number;
  maxToolResultChars: number;
  maxTotalContextChars: number;
};

type RunMetadata = {
  schemaVersion: string;
  promptVersion: string;
  toolSchemaVersion: string;
  contextPolicyVersion: string;
  model: string;
  providerBaseUrl?: string;
  modelCapabilities?: ModelCapabilities;
};

type AgentRunInput = {
  task: string;
  goal?: string;
  successCriteria?: string[];
  maxSteps?: number;
};

type LoopTurn = {
  id: string;
  runId: string;
  stepIndex: number;
  intent?: string;
  decision?: AgentDecision;
  toolResult?: ToolResult;
};

type LoopSession = {
  runId: string;
  task: string;
  status: 'running' | 'waiting_for_approval' | 'paused' | 'cancelled' | 'finished' | 'failed';
  turns: LoopTurn[];
};

type LoopControl = {
  maxSteps: number;
  cancel(): void;
  pause(reason: string): void;
  resume(): void;
};

interface ModelClient {
  complete(input: ModelInput): Promise<ModelOutput>;
}

interface ToolSpec<TArgs, TResult> {
  name: string;
  title: string;
  description: string;
  modes: ToolMode[];
  risk: ToolRisk;
  argsSchema: ZodSchema<TArgs>;
  resultSchema: ZodSchema<TResult>;
  execute(args: TArgs, ctx: ToolContext): Promise<ToolResult<TResult>>;
}

type ToolResult<TData = unknown> = {
  ok: boolean;
  code: string;
  summary: string;
  data?: TData;
  error?: {
    message: string;
    detail?: unknown;
  };
  nextHints?: string[];
  changedPage?: boolean;
  requiresObserve?: boolean;
  requiresApproval?: boolean;
  approval?: {
    reason: string;
    risk: ToolRisk;
    actionPreview?: string;
  };
  context?: {
    visibility: 'full' | 'summary' | 'hidden';
    summary?: string;
  };
};

type ApprovalRequest = {
  id: string;
  runId: string;
  stepId: string;
  tool: string;
  argsPreview: unknown;
  risk: ToolRisk;
  reason: string;
  actionPreview?: string;
  status: 'pending' | 'approved' | 'denied' | 'expired';
  createdAt: number;
  decidedAt?: number;
};

type ModelOutputTrace = {
  rawText: string;
  parsedDecision?: AgentDecision;
  parseError?: {
    code: string;
    message: string;
  };
};
```

Risk 语义：

- `safe`：纯内部或 mock 工具，不触碰真实页面。
- `low`：只读页面或配置读取。
- `medium`：可能改变页面状态的普通动作。
- `high`：提交、删除、支付、上传、剪贴板、执行 JS 等需要 approval 的动作。

ToolMode 语义：

- v0.1 采用完整 ToolSpec 形态，但不做正式 ToolSelector。
- v0.1 mock/internal 工具优先使用 `['internal']`，面向问答的只读工具可使用 `['ask']`。
- `debug`、`form`、`act`、`vision`、`advanced`、`memory` 先保留为协议枚举，后续版本再接入模式系统。

ContextPolicy 默认值：

- `maxRecentSteps`: 3
- `maxToolResultChars`: 1200
- `maxTotalContextChars`: 8000

ToolResult 进入下一轮模型上下文前必须经过 `ContextCompactor`：

- 完整 `ToolResult.data` 写入 trace，不默认进入上下文。
- 模型默认只看到 `code`、`summary`、`nextHints`、`changedPage`、`requiresObserve`。
- 完整 `ApprovalRequest` 写入 trace，模型默认只看到 approval summary。
- `context.visibility` 控制是否进入上下文：`full`、`summary`、`hidden`。

### 错误处理

所有错误必须进入 ToolResult 或 RunFailure，不允许 throw 穿透 UI/runtime 边界。

### 复用与约束

优先复用：Zod schema、统一 error code、TraceRecorder。

不要重复实现：parser、trace writer、tool registry。

### 依赖边界

`src/agent` 允许依赖：

- `src/shared`
- `src/tools/core` 的接口
- `src/storage/interfaces` 的接口
- `src/agent/model` 的接口

`src/agent` 不允许依赖：

- `chrome.*`
- `window` / `document` / `HTMLElement`
- React
- Zustand
- Dexie
- ContentRPC
- concrete page tools

v0.1 所有 agent/tools/shared/storage 单测必须能在 Node/Vitest 环境运行，不依赖 React、DOM、Chrome API、content script 或真实模型。

## 10. 验收标准

AC1. 覆盖 US1：当开发者输入测试任务时，系统能完成一次 mock agent run 并产生 finish/fail/ask_user。

AC2. 覆盖 US2：当模型输出不符合 AgentDecision schema，或使用旧的 `type: "tool"` 形态时，系统返回 parse failure 并写入 trace。

AC3. 覆盖 US3：当 tool 不存在或 args 不合法时，trace 中包含 tool name、error code、retryable 标记。

AC4. 覆盖 US4：新增 mock tool 只需要注册 ToolSpec，不需要修改 AgentLoop。

AC5. 覆盖 US5：LoopSession 能包含多个 LoopTurn，RunController 能表达 `maxSteps`、`cancel`、`pause`、`resume` 状态。

AC6. 覆盖 US6：ToolSpec 支持 `risk`；当 mock tool 返回 `requiresApproval` 时，AgentLoop 进入 `waiting_for_approval`，并写入 approval trace event。

AC7. 覆盖 US7：模型输出解析失败时，trace 记录 raw output、parse error，并标记 promptVersion、toolSchemaVersion、contextPolicyVersion、schemaVersion。

AC8. 覆盖 US8：每个 step/span 记录 startedAt、endedAt、durationMs；TraceEvent envelope 保留 timestamp。

AC9. 覆盖 US9：AgentRunInput 支持 `goal`、`successCriteria`、`maxSteps`；AgentStep 支持 `intent`，但 v0.1 不生成完整 plan。

AC10. ToolResult 完整结果写入 trace，但进入下一轮模型上下文的只有压缩摘要。

AC11. ContextCompactor 默认只保留最近 3 个 step summary，并遵守 `maxToolResultChars` 和 `maxTotalContextChars`。

AC12. v0.1 不包含 planner、任务拆解、sub-agent / agent-as-tool / delegate_to_agent 决策类型。

AC13. v0.1 agent/tools/shared/storage 单测可在 Node/Vitest 环境运行，不依赖 React、DOM、Chrome API、content script 或真实模型。

AC14. v0.1 不实现 React DevRunner；手动验证通过 dev script 完成，dev script 可在开发模式读取 `.env` fallback 配置。

AC15. 已有配置、lint、tsconfig 行为不受影响。

AC16. 实际改动不超出「改动目录结构」；如必须超出，PR 需要写偏离说明。

AC17. 不涉及设计图，设计验收为不适用。
