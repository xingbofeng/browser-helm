# v0.1 — Agent Kernel Prototype

## 1. 背景

当前项目还没有可运行的 Agent runtime。用户的最终目标是纯前端、无后端、浏览器扩展内运行的浏览器 Agent，但在做页面工具和 UI 前，必须先证明最小 loop 能稳定运行。

当前用户遇到的问题：没有统一的 AgentDecision、ToolSpec、ToolResult、TraceEvent，也没有模型调用抽象、tool registry、结构化输出解析和错误处理。

现有系统限制：无法判断模型输出是否合法，无法统一执行工具，也无法复盘一次 agent run。

为什么现在要做：v0.1 是后续 a11y tools、cockpit UI、form/debug、memory 和 workflow replay 的地基。

## 2. 用户故事

US1. 作为产品开发者，我希望在没有后端的情况下运行一个最小 agent loop，以便验证 BrowserHelm 的核心方向可行。

US2. 作为开发者，我希望模型输出必须通过 schema 校验，以便避免自然语言或坏 JSON 直接驱动工具。

US3. 当模型输出不合法时，作为开发者，我希望系统产生可诊断错误和 trace，以便定位是 prompt、parser、schema 还是模型问题。

US4. 作为后续工具开发者，我希望有统一 ToolRegistry 和 ToolResult，以便新工具可以按统一协议接入。

## 3. 目标

本 Issue 要完成：

- 建立 AgentLoop、StateMachine、StepRunner。
- 建立 PromptBuilder 和基础 system prompt。
- 建立 ModelClient 接口与 OpenAI-compatible client 骨架。
- 建立 DecisionParser，支持 tool / finish / fail / ask_user。
- 建立 ToolRegistry、ToolRouter、mock tools。
- 建立 TraceRecorder 与基础 TraceEvent schema。
- 建立 strict TypeScript + ESLint 规范。

## 4. 不做什么

本 Issue 明确不处理：

- 不做真实 DOM 读取。
- 不做正式 UI。
- 不做 content script 工具。
- 不做 memory。
- 不做 approval UI。
- 不接 OpenAI Agents SDK。
- 不接 Vercel AI SDK。

## 5. 产品方案

### 功能入口

开发者通过 background/dev command 或临时调试入口启动一次测试 run。

### 用户路径

输入任务 -> AgentLoop 构建 prompt -> ModelClient 返回 decision -> DecisionParser 校验 -> ToolRouter 执行 mock tool -> TraceRecorder 写入 step -> finish/fail/ask_user。

### 正常状态

一次 run 至少包含 started、model_decision、tool_result、finished trace。

### 空状态

没有可用模型配置时返回 `PROVIDER_NOT_CONFIGURED`。

### 错误状态

模型输出非法、tool 不存在、tool args 不合法、模型请求失败都必须进入 fail state。

### 权限 / 可见性

不涉及页面权限。API key 配置只保留接口骨架，不要求 UI。

## 7. 技术方案

### 现状

无 agent runtime。

### 目标设计

以 background 为 early host，建立独立 agent kernel。Agent kernel 不直接触碰 DOM，不依赖 UI，不依赖后端。

### 数据流 / 调用链

输入 -> AgentLoop -> PromptBuilder -> ModelClient -> DecisionParser -> ToolRouter -> TraceRecorder -> 输出。

### 关键类型 / API

```ts
type AgentDecision =
  | { type: 'tool'; name: string; args: unknown; reason: string }
  | { type: 'ask_user'; question: string }
  | { type: 'finish'; summary: string }
  | { type: 'fail'; reason: string };

interface ModelClient {
  complete(input: ModelInput): Promise<ModelOutput>;
}

interface ToolSpec<TArgs, TResult> {
  name: string;
  risk: 'read' | 'mutating' | 'sensitive' | 'internal';
  argsSchema: ZodSchema<TArgs>;
  execute(args: TArgs, ctx: ToolContext): Promise<TResult>;
}
```

### 错误处理

所有错误必须进入 ToolResult 或 RunFailure，不允许 throw 穿透 UI/runtime 边界。

### 复用与约束

优先复用：Zod schema、统一 error code、TraceRecorder。

不要重复实现：parser、trace writer、tool registry。

## 10. 验收标准

AC1. 覆盖 US1：当开发者输入测试任务时，系统能完成一次 mock agent run 并产生 finish/fail/ask_user。

AC2. 覆盖 US2：当模型输出不符合 AgentDecision schema 时，系统返回 parse failure 并写入 trace。

AC3. 覆盖 US3：当 tool 不存在或 args 不合法时，trace 中包含 tool name、error code、retryable 标记。

AC4. 覆盖 US4：新增 mock tool 只需要注册 ToolSpec，不需要修改 AgentLoop。

AC5. 已有配置、lint、tsconfig 行为不受影响。

AC6. 实际改动不超出「改动目录结构」；如必须超出，PR 需要写偏离说明。

AC7. 不涉及设计图，设计验收为不适用。
