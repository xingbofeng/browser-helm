# v1.1.3 — Public Release Readiness

## 1. 背景

v1.1.2 收口 AgentLoop、approval、prompt/context、locale 和工具可见性等主链路安全问题之后，BrowserHelm 仍不能直接对外称为稳定发布版。公开仓库当前缺少可核验 Release，`package.json` 版本仍可能与宣传版本不一致，README 的隐私和存储声明容易被误读，CI 只覆盖基础 typecheck/lint/unit/e2e/package，没有 release artifact provenance、coverage 阈值、安全扫描或权限声明检查。

当前用户遇到的问题：用户无法从 GitHub Release 判断自己安装的具体版本，也无法确认下载 zip 对应哪个 commit；审计者无法用版本号、tag、CHANGELOG 和 checksum 复盘问题；README 的“本地优先”“不上传数据”“API Key 存储”等表达若不精确，会造成错误安全预期。

现有系统限制：仓库已有 CI 和 landing package artifact，但没有 tag-triggered release workflow、SHA256 checksum、CHANGELOG、coverage gate、dependency/security scan、secret scan、manifest permission audit 或 README/docs/tool manifest 一致性检查。

为什么现在要做：v1.1.3 是第一个 public release readiness 版本。它不扩大 browser agent 能力，而是把公开发布、下载、版本追踪、CI 门槛和安全声明收敛到可审计状态。

## 2. 用户故事

US1. 作为用户，我希望 GitHub Release 中的 zip、版本号、commit、checksum 和 release notes 一致，以便安全安装和回溯问题。

US2. 作为安全敏感用户，我希望 README 清楚说明哪些数据留在本机、哪些会发送给我配置的模型 provider，以便做出知情选择。

US3. 作为开发者，我希望 CI 在发布前检查 coverage、安全扫描、工具文档一致性和 manifest 权限，以便减少公开发布事故。

US4. 作为维护者，我希望 CHANGELOG 和 release notes 自动引用本版本修复项和已知限制，以便后续 issue/bug report 能定位版本。

US5. 作为审计者，我希望 extension zip 有 SHA256 和 commit provenance，以便验证下载产物没有漂移。

## 3. 目标

本 Issue 要完成：

- 建立版本治理：`package.json`、manifest version、Git tag、CHANGELOG、release notes、landing download 和 GitHub Release 保持一致。
- 增加 release workflow：tag push 触发构建、测试、打包、生成 SHA256、上传 release artifact。
- 增加 CI release gates：coverage、dependency audit/security scan、secret scan、docs/tool manifest consistency、manifest permission audit。
- 收敛 README / README_EN / docs/security：准确说明 local-first、BYOK、云 provider 数据发送边界、API Key 存储边界和 page-health hook 行为。
- 确认 `.reasonix/`、临时测试日志、失败 artifact、个人调试文件不进入仓库或 release zip。
- 为 Chrome Web Store / 手动安装准备最小发布检查清单：权限说明、隐私声明、构建命令、产物路径、验证命令。
- 明确 v1.1.3 不代表完整平台版本：memory/workflow、CDP、完整 eval、完整 ToolSelector/i18n 仍按后续 roadmap 推进。

### 任务拆解

- T1. 将 `package.json` version、WXT manifest version 和 docs 中版本号统一到 `1.1.3` 或明确的 release candidate 版本。
- T2. 新增 `CHANGELOG.md`，记录 v1.1.2 hardening、v1.1.3 release readiness、已知限制和升级说明。
- T3. 新增 tag-triggered `release.yml`：checkout、npm ci、typecheck、lint、unit、coverage、build、e2e、zip、checksum、GitHub Release upload。
- T4. release artifact 命名包含 version 和 commit short SHA，例如 `browser-helm-v1.1.3-<sha>.zip`。
- T5. 生成并上传 `SHA256SUMS.txt`，release notes 中写明 commit、Node/WXT 版本、构建命令和校验方式。
- T6. CI 顶部设置最小 GitHub token permissions；release job 单独提升 `contents: write`。
- T7. 增加 workflow concurrency，避免旧 push artifact 与新 push 混淆。
- T8. 增加 `npm run test:coverage` 和 coverage thresholds；发布前至少覆盖 runtime、tools/core、form DOM、provider client 和 UI sanitizer 关键路径。
- T9. 增加 dependency/security scan：`npm audit --audit-level=high`，并预留 CodeQL/Semgrep 或等价静态扫描入口。
- T10. 增加 secret scan / repo hygiene check，确保 `.reasonix/`、`.env`、trace JSONL、失败测试日志不进入 git 或 release zip。
- T11. 增加 docs/tool manifest consistency check：README/docs/tools 中列出的 `bh_` 工具必须来自 ToolRegistry/TOOL_NAMES，已删除工具不得出现在主能力表。
- T12. 增加 manifest permission audit：安装权限、optional_host_permissions、web_accessible_resources、page-health-hook 暴露面必须有说明。
- T13. 修正 README / README_EN：`不上传数据` 改为“不上传到 BrowserHelm 自有后端；配置云 provider 时会发送裁剪/脱敏上下文给该 provider”。
- T14. 修正 API Key 表述：当前保存到 `chrome.storage.local`，不写入 trace/model context；不宣称静态加密，除非另行实现 WebCrypto 加密。
- T15. 增加 `docs/security.md` 发布版隐私声明：provider messages、redaction 限制、page-health hook、optional permissions、local provider risk。
- T16. 增加 `docs/release.md`：发布步骤、验证命令、checksum 验证、Chrome extension 手动安装说明、回滚方式。
- T17. 确认 landing download 产物与 GitHub Release artifact 使用同一个 zip 或同源构建，避免“官网下载”和 Release 漂移。
- T18. 增加 release smoke checklist：安装 unpacked extension、打开 side panel、配置 mock provider、页面观察、表单填写、审批拒绝、审批通过、下载 trace 脱敏检查。

## 4. 不做什么

本 Issue 明确不处理：

- 不新增 browser agent 功能，不实现 memory/workflow/CDP/vision/advanced tools。
- 不承诺 API Key 本机 profile 被盗时仍安全，除非另行实现加密与 key management。
- 不做 Chrome Web Store 正式提交流程的全部法务/商店素材，只准备技术发布清单。
- 不做完整平台 eval；这里只做 release gate 需要的 coverage/security/docs consistency。
- 不引入强制云后端，不改变 local-first 默认产品定位。

## 5. 产品方案

### 功能入口

用户从 GitHub Releases 或官网 landing download 下载扩展 zip。Release 页面展示版本号、commit、checksum、变更摘要、已知限制和安装说明。

### 用户路径

用户打开 Release -> 下载 zip 和 SHA256 -> 校验 checksum -> Chrome 加载 unpacked extension -> 设置 provider -> 使用 BrowserHelm -> 如遇问题，在 issue 中提供版本号、commit 和脱敏 trace。

### 正常状态

Release、README、landing download、package version、manifest version、CHANGELOG 一致；CI 显示 release gate 通过；用户可以复现同一版本产物。

### 空状态

如果没有正式 release，README 必须标注“development preview / release candidate”，不能宣称稳定版本。

### 错误状态

如果 release workflow 任一步失败，不创建 GitHub Release；如果 checksum 或 docs/tool consistency 不通过，阻断发布。

### 权限 / 可见性

README 和 release notes 必须明确 extension 权限、optional host permissions、page-health hook、provider 数据发送边界、API Key 存储边界和本地 provider 风险提示。

## 7. 技术方案

### 现状

当前 CI 只有 push/PR 的 typecheck、lint、unit、E2E、zip 和 landing artifact。没有 release workflow、coverage、security scan、tool docs consistency、manifest permission audit 或 checksum/provenance。

### 目标设计

发布链路固定为：

```txt
tag vX.Y.Z
  -> release workflow
  -> npm ci
  -> typecheck / lint / unit / coverage / e2e
  -> build extension zip
  -> generate SHA256SUMS
  -> create GitHub Release
  -> upload zip + checksum + release notes
  -> optionally sync landing download from same artifact
```

Release metadata 固定包含：

```txt
version
commit SHA
build timestamp
Node version
WXT version
artifact filename
SHA256
known limitations
privacy/provider boundary
verification commands
```

Docs consistency 固定检查：

```txt
ToolRegistry / TOOL_NAMES
  -> generated tool manifest JSON
  -> README/docs/tools claimed tool table
  -> mismatch fails CI
```

### 数据流 / 调用链

Git tag -> GitHub Actions release job -> npm scripts -> WXT zip -> checksum generator -> GitHub Release API -> user download / landing download。

### 关键类型 / API

```ts
type ReleaseManifest = {
  version: string;
  commitSha: string;
  artifactName: string;
  sha256: string;
  builtAt: string;
  nodeVersion: string;
  wxtVersion: string;
};

type ToolDocsCheckResult = {
  missingInDocs: string[];
  missingInRegistry: string[];
  deprecatedStillAdvertised: string[];
};
```

### 错误处理

- coverage/security/docs check 失败：阻断 release。
- checksum 生成失败：阻断 release。
- artifact upload 失败：不创建或删除 draft release。
- landing sync 失败：release 可保留，但 release notes 必须标注 landing download 未更新，或阻断发布，由维护者选择。

### 复用与约束

优先复用：现有 `npm run typecheck`、`npm run lint`、`npm test`、`npm run test:e2e`、`npm run zip`、`npm run build:landing`。

不要重复实现：构建系统、WXT zip、Playwright E2E、provider runtime。

## 10. 验收标准

AC1. `package.json` version、manifest version、CHANGELOG、Release tag 和 artifact filename 一致。

AC2. tag push 能触发 release workflow，并产出 extension zip、`SHA256SUMS.txt` 和 release manifest。

AC3. Release notes 包含 commit SHA、checksum、安装说明、隐私/provider 数据边界、已知限制和回滚说明。

AC4. README / README_EN 不再误导用户“完全不上传数据”或“API Key 加密存储”；必须明确云 provider 会接收裁剪/脱敏后的模型上下文。

AC5. CI 包含 coverage gate、安全/依赖扫描入口、secret/repo hygiene check、tool docs consistency check 和 manifest permission audit。

AC6. `.reasonix/`、`.env`、trace JSONL、失败测试日志不会进入 git 或 release zip。

AC7. docs/tools / README 工具表与 ToolRegistry/TOOL_NAMES 一致，已删除或未实现工具不会作为主能力宣传。

AC8. release smoke checklist 至少覆盖安装扩展、打开 side panel、配置 mock provider、页面观察、表单填写、审批拒绝、审批通过和 trace 脱敏。

AC9. GitHub Actions 最小权限和 concurrency 已配置，release job 只有在 tag 发布时才获得写 release 权限。

AC10. landing download 与 GitHub Release artifact 不漂移，或 release notes 明确标注不同步状态并阻断正式发布。
