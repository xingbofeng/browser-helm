# v0.3 — Structured Page Data Prototype

## 1. 背景

v0.2 已经能读取真实页面，并建立 URL、title、visible text、page state 和 stable ref map。下一步不是立刻做完整 UI，而是把页面进一步结构化成可被 Agent 和 Cockpit 稳定消费的数据层。

当前用户遇到的问题：页面 observation 有了，但交互元素、表单字段、字段状态和后续动作准备还没有清晰分层。

现有系统限制：没有统一的 interactive element schema、form field snapshot、字段状态读取和安全动作准备数据。

为什么现在要做：v0.3 是 v0.4 完整 Cockpit UI 和 v1.0 Page Inspector + Form Doctor 的数据基础。

## 2. 用户故事

US1. 作为开发者，我希望能从 ref map 派生出稳定的交互元素列表，以便后续 UI 展示和工具调用。

US2. 作为开发者，我希望能从页面中读取表单字段结构和状态，以便解释表单为什么不能提交。

US3. 作为后续 runtime 开发者，我希望 click/type/form action 之前已有可验证的数据结构，以便安全动作不直接依赖临时 DOM 猜测。

US4. 作为 UI 开发者，我希望 observation、ref、interactive elements、form fields 能作为四类 tab 数据进入 Cockpit。

## 3. 目标

本 Issue 要完成：

- 建立 structured page data 总体 schema。
- 拆分并承接 `v0.31` 交互元素、`v0.32` 表单字段、`v0.33` 基础动作准备。
- 明确四类数据：页面观察、Ref 映射、交互元素、表单字段。
- 为 v0.4 Cockpit UI 提供稳定数据 contract。
- 保持单 AgentLoop，不引入 sub-agent；结构化数据只作为 tools/UI/context summary 的输入。

### 任务拆解

- T1. 定义 structured page data 总体 contract。
- T2. 明确 observation / refs / interactive elements / form fields 的边界。
- T3. 定义 tab data adapter，供 v0.4 UI 消费。
- T4. 定义跨层错误码和 empty state。
- T5. 明确 `v0.31`、`v0.32`、`v0.33` 的依赖关系和验收边界。

## 4. 不做什么

本 Issue 明确不处理：

- 不做完整 Cockpit UI。
- 不做自动填写。
- 不做 submit-with-approval。
- 不做 DevTools/CDP。
- 不做 memory / workflow replay。
- 不做 screenshot/vision。
- 不做 sub-agent / agent-as-tool / delegate_to_agent。

## 5. 产品方案

### 功能入口

通过 v0.2 observation 和 ref map 生成结构化页面数据，供后续 tools 和 Cockpit UI 使用。

### 用户路径

observe 页面 -> 建立 ref map -> 派生交互元素 -> 读取表单字段 -> 输出四类 tab data。

### 正常状态

四类数据都能以稳定 schema 输出，并带有 summary、count、empty reason、updatedAt。

### 空状态

没有交互元素或表单字段时，返回明确 empty reason，而不是空白数组裸返回。

### 错误状态

ref stale、字段状态不可读、label 识别失败、表单关联失败都要结构化返回。

### 权限 / 可见性

本阶段默认只读，不触发页面修改。

## 7. 技术方案

### 现状

已有 page observation 和 ref map，但缺少面向 UI 与工具的二次结构化数据层。

### 目标设计

以 ref map 为基础派生 interactive elements 和 form fields。数据层不直接渲染 UI，也不执行页面动作。

### 数据流 / 调用链

bh_page_observe -> ref map -> structured data builder -> tab data adapter -> tools / cockpit / compact context summary。

### 关键类型 / API

```ts
type StructuredPageData = {
  observation: ObservationTabData;
  refs: RefTabData;
  interactive: InteractiveTabData;
  forms: FormFieldsTabData;
};
```

Context 规则：

- structured page data 的完整对象写入 trace / runtime snapshot。
- 模型上下文只接收按 mode 裁剪后的摘要，例如当前 tab summary、关键 refs、字段数量和主要问题。
- v0.3 不新增多 agent 决策类型。

### 错误处理

局部数据构建失败不阻断其他 tab data。每个 tab 都要有独立 status、summary 和 error。

### 复用与约束

优先复用：v0.2 observation、ref map、ToolResult。

不要重复实现：DOM 查询、ref 生命周期、UI store。

## 10. 验收标准

AC1. 覆盖 US1：交互元素数据能从 ref map 派生，并保留 ref_id、role、name、state。

AC2. 覆盖 US2：表单字段数据能表达 label、type、required、value state、validation 状态。

AC3. 覆盖 US3：安全动作准备数据能说明后续 action 需要哪些 ref、状态和风险信息。

AC4. 覆盖 US4：四类 tab data 都能被 v0.4 UI 直接消费。

AC5. structured page data 的完整结果不直接进入模型上下文，必须通过 context summary 裁剪。

AC6. 已有 v0.1/v0.2 行为不受影响。

AC7. 实际改动不超出「改动目录结构」；如必须超出，PR 需要写偏离说明。

AC8. 不涉及设计图，设计验收为不适用。
